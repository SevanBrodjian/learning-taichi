Recording every substep into one command buffer is the whole difference. The same 128×128 elastic step that costs 345 µs per substep in canonical Taichi/CUDA — flat in particle count, because Python pays a ~56 µs kernel launch 167 times a frame — costs 7.1 µs in WebGPU, and the 60 fps particle budget goes from 1,229 (one JavaScript thread) and zero (Taichi/CUDA from Python never reaches 60 fps at any particle count) to ~172,578. What did not come free: WGSL has no atomic float add, and the obvious fixed-point scale is wrong. At 220 quanta per particle mass the port lands 79× outside canonical's own noise band on a bouncing disk — visibly displaced, with nothing to warn you. 224 lands inside it.

Where the 345 µs went

Nothing about the arithmetic changed. The 4090 was idle, waiting to be told what to do, 668 times a frame. Both bars are an empty kernel — no work at all — measured on this machine in this session.

What WGSL forced: no atomic float add

atomic<f32> does not compile ("'atomic' only supports 'i32', 'u32' or 'vec2u'"), and P2G scatters mass and momentum as floats. Two routes were implemented and both were run against canonical ground truth on identical initial conditions. Flip the scene toggle — the gentle drop scene forgives a coarse scale and the bouncing disk does not.

fixed point, 2k quanta per particle mass exact f32 via compare-and-swap canonical's own noise band

The band is what the canonical simulator does to itself: its lower edge is the same code re-run (GPU atomics reorder between runs) and its upper edge is the same code with the initial positions nudged by one f32 rounding unit. Anything inside is indistinguishable from chaos. Note the exact-f32 point sits inside the band on both scenes but is not at zero -- a port that quantises nothing still diverges from canonical, because it dispatches in a different order and uses a closed-form polar decomposition instead of ti.svd.

The other half of the trade: range

32 bits have to cover both the resolution the physics needs and the largest value a node ever holds. Buying resolution spends range, and a saturating u32 does not raise an error — it wraps.

Measured with the exact-f32 path so the measurement cannot itself saturate. The heaviest node carries roughly 2× the particles per cell, in units of one particle mass. Read together with the accuracy result, that is the whole design rule: k ≥ 22 for accuracy, 232-k > 2 × particles-per-cell for range. The default shipped here is k=24, good to about 120 particles per cell.

Driving it over the ceiling on purpose. At 230 the accumulator holds only 4 particle masses per node while the scene needs 43; it wraps, and the block detonates. No NaN, no error, no warning — just wrong physics. 226, 224 and 222 all land on the exact-f32 result to within 2e-6.

Where the frame time actually goes

The grid sweep is flat at ~0.27 ms for every particle count: 167 dispatches over 16384 cells, almost entirely dispatch overhead. P2G — the atomic scatter — is the only part that grows, and it is what eventually ends the frame budget. CPU-side recording of all 501 dispatches costs 0.013–0.079 ms, i.e. the CPU is no longer anywhere near the critical path.

Scope. One material (elastic), one grid resolution (128×128), one adapter (nvidia / lovelace), one browser, two scenes. The accuracy conclusion is a statement about these two scenes: the coarse scale is fine on one and clearly wrong on the other, which is itself the reason not to trust a single-scene check. Nothing here was tested on the iPad or the M4, on snow/sand/fluid, or at any grid size but 128. The 60 fps particle budget is interpolated between two measured points and is measured with rendering excluded — it is a compute budget, not a full frame budget. Timing came from timestamp-query (quantum measured at 64 ns on this adapter) and from wall-clock totals over ≥30 frames, never from a single performance.now() interval.
